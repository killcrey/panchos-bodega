# CLAUDE.md

## Project Overview
"Panchos Bodega" — e-commerce storefront for The Invisible Panchos (band/brand). Single cart sells three product types: physical apparel (self-fulfilled via Shippo, or print-on-demand via Printful), digital downloads (music/art, signed download links), and free ($0, email-gated) downloads. One hidden admin panel (`?mode=admin`) handles product CRUD, inventory, and fulfillment. No test suite.

## Tech Stack & Architecture
- **Frontend**: Vanilla JS (ES modules), Vite `^8.0.12`. Single-page `index.html`; storefront vs. admin is DOM show/hide, no router, no framework.
- **Backend**: Supabase — Postgres (RLS-locked), Deno Edge Functions (`supabase/functions/*`), Storage (`bodega-images`, `audio-vault` buckets).
- **Payments**: `@stripe/stripe-js ^9.14.0`. Stripe Checkout Sessions with dynamic `price_data` — no persisted Stripe Prices; price is always read live from `products.price_cents`. Stripe Address Element (shipping) backed by Google Maps Platform autocomplete.
- **Shipping**: Shippo API (self-fulfilled) + Printful API (print-on-demand), rates fetched in parallel and summed into one Stripe shipping line. A cart can mix both.
- **DB client**: `@supabase/supabase-js ^2.108.2`.
- **Styling**: Plain CSS (`src/style.css` + inline `<style>`/`style=""` in `index.html`). No preprocessor, no utility framework.
- **Hosting**: Netlify (static `dist/`), auto-deploys `main`. Edge Functions deploy independently via Supabase CLI.

## Coding Standards & Conventions
- **Naming**: kebab-case HTML element IDs, camelCase JS vars/functions, snake_case Postgres columns/JSON metadata keys.
- **State management**: none framework-level. Admin form state lives in module-level `let`s in `main.js`, reset explicitly on modal open/close/submit. Cart state lives in `cart.js`, persisted to `localStorage`.
- **Styling**: class-based CSS in `style.css` for reusable patterns; ad hoc inline `style=""` for one-off admin UI — an accepted convention here, not something to "fix" on sight.
- **Data fetching**: `supabase.functions.invoke(name, { body })` for all edge function calls. Edge functions always re-validate price/inventory/shipping server-side — never trust client-sent amounts. Client table reads use the anon key + RLS; writes to `products`/`orders` happen only inside edge functions (service role key).
- **File input gotcha**: `<input type="file" multiple>` replaces (doesn't append to) its FileList on each reopen — accumulate selections in a JS array, reset `input.value = ''` after each `change`. See `uploadNewImageFiles`/`uploadNewDigitalFiles` in `main.js`.
- **Render-time self-healing**: prefer deriving display state from source data at render time over relying on write-time bookkeeping alone (e.g. the product card derives its audio player from `download_files` if `tracklist_snippets` is empty, and clamps `description` to `MAX_DESCRIPTION_LENGTH` regardless of what's stored). This means old rows fixed by a logic change don't need a data migration or a re-save through the admin UI.

## Deployment Protocol
- Frontend: Netlify, auto-deploys `main`. Build = `npm run build`, publish = `dist`.
- `netlify.toml` disables `SECRETS_SCAN_SMART_DETECTION_ENABLED` — every `VITE_`-prefixed key is intentionally inlined into the client bundle; never give a genuinely secret key (e.g. `service_role`) a `VITE_` prefix.
- Edge functions: not part of the Netlify build — `npx supabase functions deploy <name>` per function after any `supabase/functions/**` change. Docker warning on deploy is expected/harmless.
- Migrations: `npx supabase db push`.
- **Standing permission**: push to `origin/main` without asking first, in this repo. Still confirm before force-push, history rewrites, or destructive DB ops.

## Known Quirks & Critical Context
- **Landing page slots**: `products.landing_slot` drives the page shown right after the Enter gate — `featured` (carousel, up to 3), `latest_release`, `pancho_pick`, or null. The two single-occupancy slots are enforced by a partial unique index, so `resolveLandingSlot` in `main.js` demotes the previous holder before saving rather than letting the insert fail; the 3-featured cap can't be expressed in the DB and is checked there too. The landing page is a DOM section (`#landing-view`), not a route — `showLanding()`/`showStore(filter)` toggle it against `#store-grid`, and `applyFilter` is module-scoped so landing boxes can jump straight into a category. If no product holds any slot, `showLanding()` falls through to the store so visitors never hit an empty page.
- **Tips are the one client-chosen amount**: every product price is re-read from `products.price_cents` server-side, but a tip has nothing to validate against — `create-tip-session` defends with hard bounds only ($1–$500, `MIN_TIP_CENTS`/`MAX_TIP_CENTS`). Tip sessions carry `metadata.tip = 'true'`, which `stripe-webhook` branches on *before* the line-item loop, because that loop calls `decrement_inventory` on every line item and a tip's ad-hoc Stripe product must never reach it. Tips are nontaxable (`txcd_00000000`, `automatic_tax` off) — a gratuity isn't a sale of goods. They live in their own `tips` table (not `orders`, which is all shipping/fulfillment columns a tip never uses) and `success.html` short-circuits on `?tip=1` before calling `secure-download`, which would otherwise error on a tip that has no files.
- **`?filter=<category>` deep link**: category filters are otherwise pure in-app clicks (never reflected in the URL) — this query param, checked on initial load only (in `loadBodega`, after the `/products/<slug>/` route check and before the default landing page), lets an external link (e.g. from the main website) land directly on a specific category. Valid values are read from `.filter-btn[data-filter]` in the DOM rather than hardcoded, matched case-insensitively; `home` goes to the landing page, anything else calls `showStore`. `pancho picks` has a space, so the link needs `?filter=pancho+picks` or `%20`.
- **Per-product SEO + a real dedicated product page**: `products.slug` (unique, admin-editable, autofilled from title until touched — `wireSlugAutofill` in `main.js`) backs two things. (1) A static file per product at `dist/products/<slug>/index.html`, written by `scripts/prerender-products.js` as an extra `npm run build` step — a clone of the built `index.html` with title/meta description/canonical/OG/Twitter tags and a per-product JSON-LD `Product` block rewritten in, plus `dist/sitemap.xml` (homepage + every product), which is what makes the `Sitemap:` line in `public/robots.txt` resolve to something. This is what non-JS crawlers (Google, social link previews) see. (2) A real in-app product page for humans: `showProductPage` (`main.js`) swaps `#landing-view`/`#store-grid` for `#product-view`, rendering the full untruncated product via `renderProductMarkup`/`wireProductInteractions` — the exact same functions that build a grid card, just called with different options: the card passes `linkTitle: true, truncateDescription: true, showBuyControls: false, showDescription: false, showFullGallery: false, showAudioPreview: false`, the page passes the inverse of all six. A card is deliberately info-only — first photo, title, price, category, and sizes as plain tags — with no description, no multi-photo arrows/counter (the lightbox still gets every photo when the single visible one is clicked), no size *picker*, no buy/free-download button, and no audio play preview/tracklist; all of that only exists on the dedicated page. The whole card (photo, price/category text, size tags, empty space) is a click-to-navigate area via a delegated listener on the card itself — only `.card-play-btn`/`.track-item` (n/a on a card now that audio is page-only, but shared code) and `.product-title-link` (its own real `<a>`, to avoid double-firing) are carved out. `renderProductMarkup`'s own trailing flex spacer (`margin-top: auto`, meant to push a player/buy-button to the bottom) is only emitted when there's actually something after it to push — otherwise a now-mostly-empty card would carry dead reserved space for controls it isn't rendering. `goToProduct` (landing carousel/side-box clicks, and the initial `/products/<slug>/` route match via `matchProductFromPath`) and a card's title-link click both funnel through `showProductPage`. `updateProductUrlAndMeta` — called at the end of `showProductPage` — pushes the URL (no-op if already there) and swaps `document.title`/meta via `setProductMetaTags`. `showStore`/`showLanding` take a `{ skipHistoryUpdate }` option: by default (a real click — filter tab, footer logo, Shop Now, the product page's own Back button) they push `/` onto history if the visitor is currently on a product URL, so leaving a product always gets its own history entry; `skipHistoryUpdate: true` is used only for the initial page load and inside the `popstate` handler itself, where the browser has already moved history and pushing again would corrupt the stack mid-navigation. Without that push, two products visited back-to-back (grid → A → back to grid → B) pushed straight onto each other with no grid entry between them, so one Back press from B landed on A instead of the grid — this is what fixed it. A `popstate` listener re-derives the correct view (product page or landing) on Back/Forward, but still doesn't attempt full history fidelity — it won't restore whatever category filter was active before a product was opened, only that a product URL resolves to that product's page and everything else resolves to landing.
- **Printful two-ID system**: every Printful variant needs both a catalog `variant_id` (`/shipping/rates`) and a `sync_variant_id` (`/orders`) — stored together in `products.printful_variant_map` as `{[size]: {variantId, syncVariantId}}`.
- **Checkout ID vs. price**: `stripe_product_id` only identifies the Stripe Product. Price is always read live from `products.price_cents` via `price_data` — changing price never requires regenerating the Checkout ID.
- **Oversized apparel surcharge**: sizes are free-text per product (no fixed dropdown) — admins can type any label. Selecting 2XL/3XL/4XL/5XL (or their XXL…XXXXXL spellings) adds a flat `SIZE_UPCHARGE_CENTS` ($4) to the base price, applied client-side in `cart.js`'s `addToCart` and re-derived independently server-side in `create-checkout-session` from `item.size` — never trusted from the client cart snapshot. Applies to every fulfillment path (self-shipped and Printful alike), since it keys off the size string, not the fulfillment method. `UPCHARGE_SIZES` is duplicated in both files — keep the two lists in sync. The surcharge is currently uniform; Printful's own per-size cost is not uniform, so if it's ever made per-size, `SIZE_UPCHARGE_CENTS` becomes a per-size map in both places and the storefront hint in `main.js` needs to stop assuming one amount.
- **Payment Links are opt-in, normally skipped**: `create-stripe-link` auto-sets `skipPaymentLink=true` when Printful IDs are filled. Static Payment Links never attach a shipping charge and are never handed to customers.
- **No customer-facing "Printful" branding**: shipping labels are genericized ("Standard Shipping").
- **Digital tax codes**: products with no `weight_oz` and no Printful mapping get a Stripe Tax digital-goods code (`txcd_...`); physical items default to tangible-goods tax.
- **One shared Resend Audience ("The Invisible Panchos", live id set as `RESEND_AUDIENCE_ID`), fed three ways**: `RESEND_API_KEY` (used everywhere else for transactional email) is a send-only restricted key — confirmed live, it 401s on any Audiences/Contacts call — so contact-list management runs on a separate, more broadly-scoped key, `RESEND_CONTACTS_API_KEY`. The `addContactToAudience` helper is duplicated verbatim across three functions (this codebase's existing pattern for small per-function constants, e.g. `ADDRESS_FROM`): `free-download` calls it right after the `email_captures` insert; `stripe-webhook` calls it in the tip branch (alongside the thank-you email) and once more at the single point that covers every non-duplicate purchase — cart orders and the older static Payment Link path alike, both already funneling through the same `!isDuplicateDelivery && session.customer_details?.email` guard. The Game (`website-assets`, an unrelated Supabase project at `vihwbuiobowdreynxmgy.supabase.co` with no backend of its own — its Resend key would have to live in client-side code, which isn't safe) can't push in real time, so `sync-game-signups` pulls new rows from its `email_signups` table on a `pg_cron` schedule (every 3 hours — was 30 min initially, dropped once confirmed nothing needs that urgency — calling the function via `pg_net` with the public anon key, not a secret, and `verify_jwt = false` like its siblings, since there's nothing sensitive to protect against an early/extra invocation). `game_signup_sync_state` (single-row watermark, `id boolean primary key default true` trick to enforce exactly one row) tracks how far it's read, kept in Bodega's own DB specifically so the sync only ever needs *read* access to the Game's project — verified live with a real insert-sync-cleanup round trip, not just a connectivity check. A real Comms-page contact form on `tip-main-site` (a separate codebase) also feeds this same Audience via its own Netlify Function, independent of anything here.
- **Buyers audience, separate from the shared list**: Resend's Contacts API has no per-contact tag/property that actually persists — confirmed live by sending a `properties` object on both create and update and reading back `{}` both times. A second Audience (`RESEND_BUYERS_AUDIENCE_ID`) is the only real segmentation Resend offers. `addContactToAudience` in `stripe-webhook` takes an optional audience env-var name (defaults to the shared list); the purchase-confirmation call site (not tips) also calls it with `'RESEND_BUYERS_AUDIENCE_ID'`, so a real paying customer lands in both lists and a campaign can be sent to buyers specifically.
- **Tippers audience, a third and separate Audience from Buyers**: same non-dedup logic as Buyers — the tip branch in `stripe-webhook` calls `addContactToAudience(email)` (shared list) and `addContactToAudience(email, 'RESEND_TIPPERS_AUDIENCE_ID')` back to back, so someone who both tips and buys lands in the shared list, Buyers, *and* Tippers, not one or the other. The plan is capped at 3 Audiences ("segments") — `POST /audiences` past that returns a 400 (`"Your plan includes 3 segments. Upgrade to add more."`) — and all 3 slots were already spoken for (shared list, Buyers, and a pre-existing empty "General" audience from 2026-08-05 that predates this project's Resend work and had zero contacts). Getting a third real audience meant repurposing "General" rather than creating a fourth. There's no rename endpoint on Resend's Audiences API — both `PATCH` and `PUT /audiences/{id}` return `405`; only create/get/list/delete exist — so "General" was deleted (confirmed empty first) and a fresh "Tippers" audience created in its place, landing on the same 3-slot budget with a different name, not a true rename. `RESEND_TIPPERS_AUDIENCE_ID` is the new audience's id. Verified live: added a throwaway contact directly via the Contacts API, read it back from both the single-contact and list endpoints, then deleted it and reread to confirm the audience returned to empty. As of 2026-09-07 the `tips` table has zero rows, so there's nothing to backfill into Tippers yet. Neither Tippers nor Buyers nor the shared list gives a tipper/buyer a working opt-out today: the `unsubscribed: false` flag set on Contacts only ever matters to Resend's own Broadcast-sending feature, and the transactional sends this project actually makes (tip thank-you, order confirmation) go through the plain `/emails` endpoint with no unsubscribe link or `List-Unsubscribe` header at all — confirmed by reading `sendTipThankYouEmail`/`sendOrderConfirmationEmail` directly. A real self-service opt-out would need one added to those emails; nothing in the codebase provides it yet, for any of the three audiences.
- **Unsubscribe: a self-hosted endpoint, because Resend doesn't provide one**: confirmed against Resend's own docs — there's no managed unsubscribe URL or automatic suppression for transactional `/emails` sends; a contact's `unsubscribed` flag only ever matters to Resend's Broadcast feature, and building/hosting the endpoint is explicitly on the sender. `unsubscribe` (public, `verify_jwt = false`) is that endpoint: `GET` renders a plain confirmation/error page for a human clicking the email link, `POST` returns a bare 200/400 for RFC 8058 one-click mail-client unsubscribe (`List-Unsubscribe-Post: List-Unsubscribe=One-Click`). Both branches verify `?email=&token=` as an HMAC-SHA256(email, `UNSUBSCRIBE_SECRET`) signature before doing anything, so the link can't be used to unsubscribe an arbitrary address. On success it `PATCH`es `unsubscribed: true` by email (confirmed live that Resend's Contacts API accepts an email address in place of the contact id/uuid on `GET`/`PATCH`/`DELETE`) across all three real Audiences at once — shared list, Buyers, Tippers — rather than just the one that sent the email, since there's no reason someone who asks out would want to stay opted into a different Panchos list under the same address. `buildUnsubscribeUrl(email)` (same HMAC logic, duplicated per this project's small-helper convention) is called by every sender that also calls `addContactToAudience`: `sendOrderConfirmationEmail` and `sendTipThankYouEmail` in `stripe-webhook`, `sendDownloadEmail` and `sendTrackListEmail` in `free-download` — each appends a footer link and sets `List-Unsubscribe`/`List-Unsubscribe-Post` headers on the Resend send call. The real scope of what this stops: future Broadcast-style marketing sends only. It does **not** gate the transactional sends themselves (order confirmations, tip thank-yous, download links) — those aren't contact-status-aware at all and never were; a receipt for something someone just bought or claimed still goes out regardless of unsubscribe state, by design. Verified live end-to-end: created a throwaway Tippers contact, hit the deployed endpoint with a real HMAC token, confirmed via the Resend API that `unsubscribed` flipped from `false` to `true`, then deleted the test contact. Confirmed the invalid-token path separately (wrong token → the "invalid" page on `GET`, bare `400` on `POST`).
- **`checkout.session.completed` alone isn't proof of payment**: the webhook now also checks `session.payment_status !== 'paid'` and skips (no order, no fulfillment, no email) if it isn't — a checkout *session* can complete before payment actually clears for delayed-notification methods (some bank debits, buy-now-pay-later), and fulfilling on "completed" alone would ship before money arrives if any such method is ever enabled on the Stripe account. Also now listens for `checkout.session.async_payment_succeeded` (treated identically once matched) so a delayed payment that does clear later still produces an order — previously that event type wasn't handled at all, so it would've been silently dropped. Whether Stripe actually delivers that event type to this endpoint depends on the Dashboard's webhook subscription list, which isn't visible from code.
- **`audio-vault` is a private bucket — `get-playback-url` is how anything in it ever gets played**: it was public until this was found and fixed; the products table's own public `SELECT` (the same query the storefront already runs) put every digital file's full-quality, permanently-downloadable URL in cleartext in the API response — no purchase or email-gate involved, just reading product data. `card-play-btn`/`.track-item` clicks (`wireProductInteractions` in `main.js`) now call `get-playback-url` with the stored URL and get back a fresh one-hour signed link before calling `playGlobalTrack`, instead of ever using the stored URL directly. `secure-download`/`free-download` were already using `createSignedUrl` internally and needed no changes. `get-playback-url` itself is deliberately public/ungated — that's what preview playback already was and still is (the *entire* track, not a trimmed clip — a pre-existing product decision, unchanged here); the fix is that the deliverable is now a short-lived link instead of a permanent public one, not that playback became harder to reach. `bodega-images` is a separate bucket and stayed public on purpose — product photos are meant to be public.
- **Mixed-cart shipping**: composite rate IDs join up to two components with `::` (`shippoRateId::printfulRateId`, `printful::rateId`, or a plain Shippo ID) — always re-parsed/re-validated server-side in `create-checkout-session`, never trusted from the client.
- **Digital-file bundles can mix audio with non-audio files** (cover art, tracklist images uploaded alongside tracks). `processDigitalFiles` derives the tracklist from whichever files are actually audio, not from an "every file must be audio" check — and the card render path independently re-derives playable tracks from `download_files`, so a bundle saved before this logic existed still gets a player without a re-upload.
- **Description hard cap**: `MAX_DESCRIPTION_LENGTH` in `main.js` (currently 400) must match the `maxlength` on `#upload-description`/`#edit-description` in `index.html`. Enforced at save time (form) and on the grid card (`renderProductMarkup` called with `truncateDescription: true`) — the dedicated product page deliberately passes `truncateDescription: false` and shows the full text, since the cap exists for a small tile, not a page with room for it.
- **Lightbox z-index**: `#lb-close` must keep an explicit `z-index` — the image row is `position: relative; width: 100%`, and on any viewport ≤900px wide its edge lines up with the close button; without an explicit z-index, DOM-order stacking makes the row swallow the click.
- **Product card bottom layout**: the flex-grow spacer sits *before* the audio player (not on the Buy Now button) so leftover vertical space collects above the player, not between the player and Buy Now.
- **`.update()` under RLS lies by omission**: `supabase.from(...).update(...)` that matches zero rows (RLS blocked it, or the `.eq()` just didn't match anything) returns `{ error: null }` — no error, no signal anything went wrong. Found live: the site-settings save button reported "Saved." while the database still had the old value. Fixed by chaining `.select()` and checking the returned array is non-empty before claiming success (`settings-save-btn` handler in `main.js`) — the same check belongs on any *other* admin `.update()` call added later, not just this one.
- **Admin-editable email notes** (`site_settings`, single-row like `game_signup_sync_state`): `purchase_thank_you_message` is appended near the sign-off of both the order confirmation email and the free-download email (shared `customMessageBlockHTML` helper, duplicated in `stripe-webhook` and `free-download` per this project's existing per-function-constant convention); `tip_thank_you_message` is separate and only appears on the tip thank-you email. Both blank by default — no note isn't an error state, every email works the same either way. Edited from the admin's **Messages** tab.
- **Services are `products` with `category = 'services'`, not a separate system**: the "SERVICES" filter tab and the "Services" upload-category option already existed with no behavior wired to them before this. A service's real price depends on details a cart can't collect (date, venue, scope), so it deliberately never reaches Stripe checkout — `computeProductFlags` adds `isService = product.category === 'services'`, which changes only two things: the price line reads "Starting at $X" (or "Custom Pricing" at $0) instead of a plain price, and the buy button on the dedicated product page (cards never show buy controls at all — pre-existing, see the per-product SEO note above) reads "Request a Quote" and opens `#service-inquiry-modal` instead of adding to cart or opening the free-download modal — this is what happens when a service is left at the default Pricing Mode (`standard`); see the Pricing Mode bullet below for Free/Offer Based/Reserve, which override it. That modal posts to `submit-service-inquiry` (public, `verify_jwt = false`), which snapshots the product's title (so an inquiry stays readable if the listing is later renamed/deleted), inserts into `service_inquiries`, emails `info@theinvisiblepanchos.com` with `reply_to` set to the requester, and sends the requester a short "we got it" confirmation — deliberately with no Resend Audience add and no unsubscribe link, since an inquiry is a lead, not a subscriber, and the unsubscribe machinery documented above only exists for senders that also call `addContactToAudience`. `service_inquiries` has the same RLS posture as `tips`/`orders` (`to authenticated`, no public policy) — the admin's new **Inquiries** tab reads it directly with the anon key the same way Tips/Orders/Email Captures already do, gated by real Supabase auth, not by the `?mode=admin` URL. It follows the Orders "active queue" convention, not the Tips "full ledger" one: `loadAdminServiceInquiries` only selects `status = 'new'`, and "Mark Handled" updates that row's status and drops it off the list — a `service_inquiries` row inherently needs a human follow-up per inquiry, unlike a tip. Verified live: seeded a throwaway services-category product, submitted a real inquiry through the deployed modal/function, confirmed the row landed with the correct snapshot/budget/message, then deleted the test product and inquiry.
- **Pricing Mode (`products.pricing_mode`), available on every product regardless of category**: `standard` (default) is a no-op that preserves every existing product's behavior exactly — a service still shows "Request a Quote", everything else still checks out at `price_cents`. The other three are opt-in:
  - `free` — price forced to $0 (`readPricingModeFields` in `main.js` sets it at save time), "Get It Free", the existing `free-download` flow unchanged. Digital-only by nature, so Sizes/Weight/Printful/Inventory/Stripe-ID-generation all hide regardless of category (`updateSizesVisibility`/`updateWeightVisibility` in `main.js` now take `pricingMode`, not just category).
  - `offer_based` — the buyer names a price within `offer_min_cents`/`offer_max_cents` (two new columns) instead of a fixed one, "Make an Offer". A physical/digital item (any category but Services) still goes through the *normal* cart: `openOfferModal` collects the amount, `addToCart` in `cart.js` takes an `offerAmountCents` override that stands in for `product.price_cents` on that line, and `create-checkout-session` re-clamps it server-side against the product's own bounds before charging anything — never trusts the client, same discipline as the size upcharge right next to it. A **service** has no cart entry point at all (never did), so its Offer Based goes through the same standalone-session path as Reserve instead (see below) — `openOfferModal` branches on `product.category === 'services'` to decide which of the two it does.
  - `reserve` — **Services only** (the dropdown's `reserve` `<option>` is `disabled` outside Services in both the upload and edit forms, and `create-product-payment-session` rejects any non-service product server-side too — "applied toward the final price" only means something when there's a booking to apply it to). Price locked to a fixed `RESERVE_DEPOSIT_CENTS` ($25, a constant, not per-product — matches what was asked for), "Reserve".
  Offer Based-for-services and Reserve share one new edge function, `create-product-payment-session` — same ad-hoc/no-cart shape as `create-tip-session` (dynamic `price_data`, no persisted `stripe_product_id`, `automatic_tax` off with the nontaxable code, since a deposit or a custom offer isn't a sale of tangible goods) rather than the products-cart-Stripe pipeline, since a service was never in that pipeline to begin with. Both land in a new `product_payments` table (same rationale `tips` got its own table: no shipping/fulfillment columns to fill) via a new `stripe-webhook` branch keyed on `session.metadata.productPayment === 'true'`, checked right alongside the existing `tip` branch — inserts the row, emails the payer (`sendProductPaymentEmail`, branches on `reserve` vs `offer_based` copy), and adds them to the shared list + Buyers audience (real revenue, not a lead). `success.html`/`success.js` short-circuits on `?service=1` the same way it already did on `?tip=1` — nothing to unlock for either.
  **Admin form field-graying** (`updatePricingModeUI(prefix)` in `main.js`, called on both category-change and pricing-mode-change, for both the upload form and the edit modal): Services always hides Inventory/Sizes/Weight/Printful/the "Generate Checkout ID" section, regardless of pricing mode — none of the four service modes ever touch `stripe_product_id`. On top of that, Free and Reserve hide Inventory/Weight/Printful/Sizes/Stripe-ID for *any* category (both are cart-free, non-shipping flows); Offer Based leaves all of those enabled outside Services, since a physical Offer Based item (e.g. a CD) still ships and still needs a real Stripe Product for `price_data` exactly like a Standard item does. Switching category away from Services while Reserve is selected auto-resets the dropdown to Standard and clears the stale locked `$25` value, rather than leaving a Reserve-shaped price behind silently.
  Verified live: exercised the admin form's graying matrix via simulated category/pricing-mode change events (all six combinations checked programmatically, not eyeballed); seeded three throwaway products (a service Offer Based, a service Reserve, a non-service/music Offer Based with a real bare Stripe Product) and drove each end to end — confirmed `create-product-payment-session` actually clamps an out-of-bounds offer to the stored max (requested $500 against $20–$100 bounds, Stripe session's real `amount_total` came back exactly $100) and forces Reserve to exactly $25 regardless of what's sent; confirmed `create-checkout-session`'s cart-side offer clamping the same way (requested $999.99 against $5–$50 bounds on the CD, real line-item `unitAmountCents` came back exactly $50); confirmed the non-service Offer Based modal actually adds to `cart.js`'s `localStorage` cart with the chosen `offerAmountCents`. Did not complete a real payment (live-mode Stripe key) — cleaned up all three test products and the throwaway Stripe Product (deactivated, not deleted — Stripe doesn't allow deleting a Product with Prices attached) afterward.
- **Admin dashboard is tabbed, not columned**: Inventory/Orders/Tips/Email Captures/Inquiries/Messages each get their own always-visible flex column — cramped on desktop with several, a long stack on mobile. Now one `.dashboard-panel-tabs` panel (flex: 3, matching the combined width of what it replaced) holds all six as `.admin-tab-panel`s, toggled by `.admin-tab-btn` clicks (plain `style.display = 'flex'/'none'` — a panel must stay `display:flex` when shown, not `block`, or its list's own `overflow-y:auto` breaks).
