# CLAUDE.md

## Project Overview
"Panchos Bodega" — e-commerce storefront for The Invisible Panchos (band/brand). Single cart sells three product types: physical apparel (self-fulfilled via Shippo, or print-on-demand via Printful), digital downloads (music/art, signed download links), and free ($0, email-gated) downloads. One hidden admin panel (`?mode=admin`) handles product CRUD, inventory, and fulfillment. No test suite.

## Tech Stack & Architecture
- **Frontend**: Vanilla JS (ES modules), Vite `^8.0.12`. Single-page `index.html`; storefront vs. admin is DOM show/hide, no router, no framework.
- **Backend**: Supabase — Postgres (RLS-locked), Deno Edge Functions (`supabase/functions/*`), Storage (`bodega-images`, `audio-vault` buckets).
- **Payments**: `@stripe/stripe-js ^9.14.0`. Stripe Checkout Sessions with dynamic `price_data` — no persisted Stripe Prices; price is always read live from `products.price_cents`. Stripe Address Element (shipping) backed by Google Maps Platform autocomplete.
- **Shipping**: Shippo API (self-fulfilled) + Printful API (print-on-demand), rates fetched in parallel and summed into one Stripe shipping line. A cart can mix both.
- **DB client**: `@supabase/supabase-js ^2.108.2`.
- **Styling**: Plain CSS (`src/style.css` + inline `<style>`/`style=""` in `index.html`). No preprocessor, no utility framework.
- **Hosting**: Netlify (static `dist/`), auto-deploys `main`. Edge Functions deploy independently via Supabase CLI.

## Coding Standards & Conventions
- **Naming**: kebab-case HTML element IDs, camelCase JS vars/functions, snake_case Postgres columns/JSON metadata keys.
- **State management**: none framework-level. Admin form state lives in module-level `let`s in `main.js`, reset explicitly on modal open/close/submit. Cart state lives in `cart.js`, persisted to `localStorage`.
- **Styling**: class-based CSS in `style.css` for reusable patterns; ad hoc inline `style=""` for one-off admin UI — an accepted convention here, not something to "fix" on sight.
- **Data fetching**: `supabase.functions.invoke(name, { body })` for all edge function calls. Edge functions always re-validate price/inventory/shipping server-side — never trust client-sent amounts. Client table reads use the anon key + RLS; writes to `products`/`orders` happen only inside edge functions (service role key).
- **File input gotcha**: `<input type="file" multiple>` replaces (doesn't append to) its FileList on each reopen — accumulate selections in a JS array, reset `input.value = ''` after each `change`. See `uploadNewImageFiles`/`uploadNewDigitalFiles` in `main.js`.
- **Render-time self-healing**: prefer deriving display state from source data at render time over relying on write-time bookkeeping alone (e.g. the product card derives its audio player from `download_files` if `tracklist_snippets` is empty, and clamps `description` to `MAX_DESCRIPTION_LENGTH` regardless of what's stored). This means old rows fixed by a logic change don't need a data migration or a re-save through the admin UI.

## Deployment Protocol
- Frontend: Netlify, auto-deploys `main`. Build = `npm run build`, publish = `dist`.
- `netlify.toml` disables `SECRETS_SCAN_SMART_DETECTION_ENABLED` — every `VITE_`-prefixed key is intentionally inlined into the client bundle; never give a genuinely secret key (e.g. `service_role`) a `VITE_` prefix.
- Edge functions: not part of the Netlify build — `npx supabase functions deploy <name>` per function after any `supabase/functions/**` change. Docker warning on deploy is expected/harmless.
- Migrations: `npx supabase db push`.
- **Standing permission**: push to `origin/main` without asking first, in this repo. Still confirm before force-push, history rewrites, or destructive DB ops.

## Known Quirks & Critical Context
- **Landing page slots**: `products.landing_slot` drives the page shown right after the Enter gate — `featured` (carousel, up to `MAX_FEATURED_PRODUCTS` — 6, raised from 3 on 2026-09-13), `latest_release`, `pancho_pick`, or null. The two single-occupancy slots are enforced by a partial unique index, so `resolveLandingSlot` in `main.js` demotes the previous holder before saving rather than letting the insert fail; the featured cap can't be expressed in the DB and is checked there too, mirrored by the same constant at render time (`renderLandingPage`'s `landingFeatured = products.filter(...).slice(0, MAX_FEATURED_PRODUCTS)`) so the two can't drift apart. Unlike the single-occupancy slots (unambiguous — there's only one to demote), hitting the Featured cap can't auto-pick which one to bump, so it opens `#featured-full-modal` (a `pickFeaturedToReplace(products)` promise, resolving to the chosen id or `null` on cancel) listing the current titles as buttons — cancelling falls back to the original hard "Clear one first" error rather than silently doing nothing. Both of `resolveLandingSlot`'s demotion `.update()` calls chain `.select()` and check the row count came back non-zero before returning success, per the `.update() lies by omission` note below — verified live (via a temporary `window`-exposed test hook, removed before commit) that the modal opens with the right list, resolves to the clicked id, and resolves to `null` on cancel/backdrop-click; the 3→6 raise was verified the same way, feeding `renderLandingPage` 8 synthetic featured products and confirming it capped at exactly 6 (6 carousel dots, not 8 or 3). The landing page is a DOM section (`#landing-view`), not a route — `showLanding()`/`showStore(filter)` toggle it against `#store-grid`, and `applyFilter` is module-scoped so landing boxes can jump straight into a category. If no product holds any slot, `showLanding()` falls through to the store so visitors never hit an empty page.
- **Tips are the one client-chosen amount**: every product price is re-read from `products.price_cents` server-side, but a tip has nothing to validate against — `create-tip-session` defends with hard bounds only ($1–$500, `MIN_TIP_CENTS`/`MAX_TIP_CENTS`). Tip sessions carry `metadata.tip = 'true'`, which `stripe-webhook` branches on *before* the line-item loop, because that loop calls `decrement_inventory` on every line item and a tip's ad-hoc Stripe product must never reach it. Tips are nontaxable (`txcd_00000000`, `automatic_tax` off) — a gratuity isn't a sale of goods. They live in their own `tips` table (not `orders`, which is all shipping/fulfillment columns a tip never uses) and `success.html` short-circuits on `?tip=1` before calling `secure-download`, which would otherwise error on a tip that has no files.
- **`?filter=<category>` deep link**: category filters are otherwise pure in-app clicks (never reflected in the URL) — this query param, checked on initial load only (in `loadBodega`, after the `/products/<slug>/` route check and before the default landing page), lets an external link (e.g. from the main website) land directly on a specific category. Valid values are read from `.filter-btn[data-filter]` in the DOM rather than hardcoded, matched case-insensitively; `home` goes to the landing page, anything else calls `showStore`. `pancho picks` has a space, so the link needs `?filter=pancho+picks` or `%20`.
- **Per-product SEO + a real dedicated product page**: `products.slug` (unique, admin-editable, autofilled from title until touched — `wireSlugAutofill` in `main.js`) backs two things. (1) A static file per product at `dist/products/<slug>/index.html`, written by `scripts/prerender-products.js` as an extra `npm run build` step — a clone of the built `index.html` with title/meta description/canonical/OG/Twitter tags and a per-product JSON-LD `Product` block rewritten in, plus `dist/sitemap.xml` (homepage + every product), which is what makes the `Sitemap:` line in `public/robots.txt` resolve to something. This is what non-JS crawlers (Google, social link previews) see. (2) A real in-app product page for humans: `showProductPage` (`main.js`) swaps `#landing-view`/`#store-grid` for `#product-view`, rendering the full untruncated product via `renderProductMarkup`/`wireProductInteractions` — the exact same functions that build a grid card, just called with different options: the card passes `linkTitle: true, truncateDescription: true, showBuyControls: false, showDescription: false, showFullGallery: false, showAudioPreview: false`, the page passes the inverse of all six. A card is deliberately info-only — first photo, title, price, category, and sizes as plain tags — with no description, no multi-photo arrows/counter (the lightbox still gets every photo when the single visible one is clicked), no size *picker*, no buy/free-download button, and no audio play preview/tracklist; all of that only exists on the dedicated page. The whole card (photo, price/category text, size tags, empty space) is a click-to-navigate area via a delegated listener on the card itself — only `.card-play-btn`/`.track-item` (n/a on a card now that audio is page-only, but shared code) and `.product-title-link` (its own real `<a>`, to avoid double-firing) are carved out. `renderProductMarkup`'s own trailing flex spacer (`margin-top: auto`, meant to push a player/buy-button to the bottom) is only emitted when there's actually something after it to push — otherwise a now-mostly-empty card would carry dead reserved space for controls it isn't rendering. `goToProduct` (landing carousel/side-box clicks, and the initial `/products/<slug>/` route match via `matchProductFromPath`) and a card's title-link click both funnel through `showProductPage`. `updateProductUrlAndMeta` — called at the end of `showProductPage` — pushes the URL (no-op if already there) and swaps `document.title`/meta via `setProductMetaTags`. `showStore`/`showLanding` take a `{ skipHistoryUpdate }` option: by default (a real click — filter tab, footer logo, Shop Now, the product page's own Back button) they push `/` onto history if the visitor is currently on a product URL, so leaving a product always gets its own history entry; `skipHistoryUpdate: true` is used only for the initial page load and inside the `popstate` handler itself, where the browser has already moved history and pushing again would corrupt the stack mid-navigation. Without that push, two products visited back-to-back (grid → A → back to grid → B) pushed straight onto each other with no grid entry between them, so one Back press from B landed on A instead of the grid — this is what fixed it. A `popstate` listener re-derives the correct view (product page or landing) on Back/Forward, but still doesn't attempt full history fidelity — it won't restore whatever category filter was active before a product was opened, only that a product URL resolves to that product's page and everything else resolves to landing.

  **Cart-line title/size are now capped before going into Stripe metadata (2026-09-14, from the security audit's Pass 1 LOW finding)**: `create-checkout-session` packs each cart line as `JSON.stringify(orderItem)` into its own metadata value, and Stripe caps every metadata value at 500 characters — `title` has no length limit anywhere in the admin form (this codebase already has real titles 60-90+ characters), so a long enough title/size combination could have made Stripe reject session creation outright. A new `truncateForMetadata(value, maxLen)` helper caps `title` at 200 and `size` at 40 before they're pushed into `orderItems` — both generous relative to real data today, but mathematically guaranteed safe (hand-verified worst case: 200-char title + 40-char size + max-length category + max-digit numeric fields serializes to 434 characters, comfortably under the 500 cap). Only affects the `order_items.product_title` snapshot, never the real `products.title` a few columns over. Verified live: seeded a throwaway product with a real 300-character title, called the actual deployed function (a real, uncharged session, expired immediately after) — session creation succeeded with the title correctly truncated to `199 chars + "…"` and total serialized length 365.
  **A bad shipping address can now be corrected from the admin instead of only retried unchanged (2026-09-14, from the security audit's Pass 3 MEDIUM finding)**: `purchase-shipping-label` (and `retry-printful-order`) always rebuilt the carrier request straight from the order's stored `shipping_*` columns, unchanged — so a genuinely bad address (typo'd street, bad zip) failed the exact same way on every "Retry Label" click, with no admin-facing fix short of editing the row directly in Supabase's own Table Editor. `loadAdminOrders` (`src/main.js`) now renders an "Edit Address" button on any shipping order, toggling an inline form (the same `shipping_*` fields, pre-filled) with a "Save Address" button that writes them directly through the admin's existing anon-key client — the same `to authenticated using (true)` RLS path `markShippedBtn` already uses, so no new edge function was needed — and, per the `.update() lies by omission` note below, chains `.select()` and checks the returned row count before claiming success rather than trusting a bare `{ error: null }`. Since `purchase-shipping-label`/`retry-printful-order` already read these columns live on every call, correcting them here is immediately picked up by the next retry with no other change required. A small local `escapeAttr` helper guards the new inputs' `value=""` attributes — a customer-typed address landing unescaped in an HTML attribute could break the markup or inject a script tag into the admin's own view. Verified live: built and ran the dev server, exercised the render/toggle/save logic via a temporary `window`-exposed hook feeding a fake order (removed before commit) — the button only renders for shipping orders, the panel toggles correctly, a name containing `"`/`<`/`>` round-trips through the attribute back to the exact original string, and a blocked/failing save (both a malformed id and a well-formed-but-RLS-blocked one) is caught and alerted rather than silently reported as saved.
  **A genuinely failed order write no longer disappears behind a silent 200 (2026-09-14, from the security audit's Pass 1 CRITICAL "any failure while writing the order is swallowed" finding)**: every internal step in `stripe-webhook`'s purchase handler (tip insert, product-payment insert, the order/order_items insert + fulfillment block) used to have its own `try { ... } catch (err) { console.error(...) }` that logged and fell through to the same unconditional `return 200` — so a transient Supabase outage or RLS misconfiguration during order creation permanently lost that order (money taken, no `orders` row, no fulfillment, nothing but a log line nobody reads) with no way for Stripe to ever retry, since a 200 tells Stripe "delivered, don't resend." The tip and product-payment branches now return a real `500` on a genuine (non-duplicate) insert failure — trivially safe to retry, since both inserts are already guarded by a real unique constraint on `stripe_session_id`; a retry either succeeds for real or cleanly re-hits the existing `23505` duplicate check. The order-write branch needed more than a status-code flip: the audit's own suggested fix ("safe once the idempotency findings are fixed") didn't account for the `processed_webhook_sessions` ledger (added for the inventory-idempotency fix below) already gating the whole block — a naive retry would just hit that same ledger row as a duplicate and bail out before ever reaching the order-write code again, still losing the order. Fixed by giving the ledger's duplicate check a second branch: for a cart-order session (`item_count` present), a duplicate ledger hit now queries whether a matching `orders` row actually exists — if not, `isRetryRecovery = true`: skip decrementing inventory again (already done on the first attempt; `decrement_inventory` has no idempotency key of its own) but still retry writing the order, returning `500` again if it still fails. A static Payment Link session (no `item_count`, never gets an `orders` row regardless — see the still-open Pass 3 CRITICAL below) has nothing to recover and still returns a plain duplicate `200`. Verified live via a throwaway debug function (deployed and deleted after) sending real, correctly-signed test events (`stripe.webhooks.generateTestHeaderString`, using the real live `STRIPE_WEBHOOK_SECRET`) to the actual deployed webhook against throwaway tracked-inventory test products, never a real charge: a pre-seeded duplicate ledger row with no order caused a retry to skip the decrement (inventory unchanged) while still writing the order and returning `200`; a genuinely malformed line-item payload caused a fresh delivery to decrement once and return `500` instead of a silent `200`, and redelivering that same broken payload returned `500` again without decrementing a second time — confirming the recovery path doesn't reintroduce the double-decrement bug even under repeated retries of a payload that can never succeed.
  **Timeouts added to every external fetch in the payment/fulfillment path, plus a size-validation gap closed (2026-09-14, from the security audit's Pass 3 and Pass 4 findings)**: no call to Shippo, Printful, or Resend anywhere in `stripe-webhook`, `create-checkout-session`, or `purchase-shipping-label` (or the new `retry-printful-order`) had a timeout — a genuinely hung third-party endpoint could block a handler indefinitely, up to the Edge Function platform's own execution ceiling, which is the one scenario where Stripe would receive something other than the usual 200 and retry the whole event (a real trigger for the inventory-idempotency issue fixed separately, if it were ever to happen). Each of those four functions now has its own small `fetchWithTimeout` helper (`AbortController`, 15s default — duplicated per-function, matching this project's existing small-helper convention, since Deno Edge Functions can't easily share code across separate deployments) wrapping every raw `fetch()` call, and every `new Stripe(...)` client in those files now also sets `timeout: 15000` (the Stripe SDK's own built-in option, covering session creation, `listLineItems`, `sessions.list`, etc. without needing to wrap each call individually). Separately, `create-checkout-session`'s size check (`if (product.sizes && !item.size)`) only ever verified that *some* size string was present, never that it was actually one of the admin's configured sizes — a stale cart or a modified request could submit any arbitrary string and have it accepted, stored as-is on `order_items.size`. Now validates membership in `product.sizes.split(',').map(s => s.trim())`, with the same fail-closed behavior the Printful-variant lookup right below it already had. Verified live: an invalid size (`"not-a-real-size"`) against a real apparel product with `sizes: "S,M,L,XL,2XL,3XL"` is now correctly rejected (`"Select a valid size..."`); a valid one (`"M"`) passes through cleanly to the next check; a full real (uncharged, then-expired) session creation for a digital item still succeeds end-to-end with the new Stripe SDK timeout in place, confirming it doesn't interfere with normal operation.
  **Failed Printful orders can now be retried from the admin (2026-09-14, from the security audit's Pass 3 HIGH finding)**: `submitPrintfulOrder` (inside `stripe-webhook`) has always recorded a failure clearly (`printful_order_status: 'failed'`, the real error, shown as a red badge in `loadAdminOrders`) — but there was no way to actually resubmit it short of manually re-creating the order in Printful's own dashboard. New function `retry-printful-order` mirrors `purchase-shipping-label`'s exact shape (admin-`.auth.getUser()`-gated, re-reads the order + its `order_items`, resubmits with `confirm: true`, writes the same status columns back) and a matching "Retry Printful Order" button appears in the admin next to a failed order. Verified live: confirmed the deployed function's admin-auth gate rejects a plain anon-key request; separately exercised the actual fetch-order/call-Printful/update-on-failure logic (skipping only the auth check, already verified) against a real throwaway order with a deliberately invalid `sync_variant_id` — Printful correctly rejected it (`"Item 0: Sync variant not found"`), and that real error correctly overwrote the row's `printful_order_error`, confirming the update-on-failure path works without ever risking an accidental real fulfillment.
  **Refunds and disputes now update Supabase instead of leaving zero trace (2026-09-14, from the security audit's Pass 1 "Event coverage" finding)**: `stripe-webhook` previously handled only `checkout.session.completed`/`async_payment_succeeded` — a refund or dispute from the Stripe Dashboard had no effect anywhere in this database; the `orders` row (or `tips`/`product_payments` row) just sat there looking like a normal, still-valid sale forever. Added handling for `charge.refunded` and `charge.dispute.created`/`.updated`/`.closed`. Neither event carries the original Checkout Session, only a Charge/PaymentIntent — and none of `orders`/`tips`/`product_payments` store a `payment_intent`, only `stripe_session_id` — so a new shared helper, `findPaymentRecordByPaymentIntent`, looks the session up via `stripe.checkout.sessions.list({ payment_intent })` (Stripe supports finding a session by the payment_intent it produced) and then checks all three tables by `stripe_session_id` for a match, since a refund/dispute can land on a cart order, a tip, or a service payment alike. New `refund_status`/`refunded_amount_cents`/`dispute_status` columns on all three tables, surfaced as red badges in the admin (Orders, Tips, and the Service Payments list). Deliberately does **not** auto-restock inventory or auto-email anyone — a refund can be partial or unrelated to a real return, so that call is left to the admin; this only makes sure they can find out it happened at all. **This code doing nothing yet doesn't mean it's not going to work — it means these event types most likely aren't even subscribed to on the Stripe Dashboard's webhook endpoint yet** (this project's own prior notes already flagged that the actual subscription list "isn't visible from code"); the Dashboard's webhook endpoint needs `charge.refunded`, `charge.dispute.created`, `charge.dispute.updated`, and `charge.dispute.closed` added to its event list for any of this to ever actually run. Verified live (read-only, no mutation): looked up a real historical order's Stripe session, got its `payment_intent`, and confirmed `sessions.list({ payment_intent })` correctly returns that exact same session back — the core lookup mechanism this whole feature depends on. Did not (and structurally could not, without a real refund/dispute or a test-mode Stripe environment neither of which exist here) exercise the two webhook branches themselves end-to-end.
  **Inventory idempotency + oversold-detection fix (2026-09-14, from the security audit's Pass 1 CRITICAL / Pass 4 HIGH findings)**: `stripe-webhook`'s per-line-item loop (inventory decrement, download-block building) used to run unconditionally on *every* delivery of `checkout.session.completed`/`async_payment_succeeded`, including Stripe's own retries — a redelivery would decrement real stock a second time for one real sale, and the only prior dedup (a racy check-then-insert in front of `orders`) never covered a static Payment Link purchase at all, since that path never got an `orders` row regardless. Fixed with one new table, `processed_webhook_sessions` (`stripe_session_id` primary key, service-role-only, no policies — same posture as `game_signup_sync_state`), inserted into atomically as the very first thing this branch does; a losing/duplicate delivery gets a clean `23505` and returns `200` immediately, before touching inventory or sending anything. A genuine (non-duplicate) insert failure now returns `500` instead of swallowing it — the one place in this handler that actually asks Stripe to retry rather than silently treating an unrecorded delivery as handled. Separately, `decrement_inventory` — confirmed *live*, for the first time, to actually exist (deploying the replacement migration hit "cannot change return type of existing function," which is what proved it) — was rewritten from a `void`-returning unknown into a single atomic conditional `UPDATE ... WHERE inventory_count >= p_quantity`, so two concurrent decrements of the same product can't both succeed past what's actually in stock and `inventory_count` can never go negative; it now returns the quantity actually decremented (`0` = tracked stock was already exhausted — "oversold" — `p_quantity` unchanged = either a normal decrement or untracked/unlimited stock, which the function now explicitly treats as always-available rather than accidentally matching a null-guard).
